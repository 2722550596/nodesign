# world 形态:落地 plan 与预期完成全景

2026-07-31。第三种产物形态「世界」(暂名 world),一个底座两种玩法:小说模式与 RP 模式。本文三块:预期完成全景图、分阶段 plan、漏洞清单。开头先放代码核实结果,因为其中一条推翻了设计的一个前提。

---

## 〇、材料勘误(先读这段,后面所有结论以此为准)

设计讨论里的说法,逐条对过代码之后,有五处需要修正。

### 1. 「任务目录里已经有 .git」不成立,这是最大的一条

核实路径:`server/projects/workspace.js`。git 仓在 `sessions/<sid>/.git`(ensureSessionWorkspace 里 init),而任务目录物理上在 `shared/tasks/`,会话里的 `tasks/` 只是一条指向它的软链(workspace.js 346 行附近)。git 不跟随软链:`git add -A` 把 `tasks` 存成一个 mode 120000 的软链对象,任务文件的内容从来没有进过任何 git 历史。已在线上实测确认:随便挑一个会话仓 `git cat-file -p HEAD^{tree}`,`tasks` 就是一个 120000 blob,且该仓只有一条 init commit。

连带发现一个现存问题:`api/canvas.js` 的 PUT 落盘链路对 `tasks/` 下的文件调用了 `commitWorkspace`,但因为上述原因,`git status --porcelain` 看不到任务文件变化,commit 静默返回 null。站点编辑的「历史 / 回退」对任务文件当前是空转的,回退按钮只能还原会话根下的旧式 canvas.html。这一条与 world 无关,但值得单独修。

结论:「世界的历史 = git log」这个架构决定本身仍然成立,但前提设施要新建:在 `shared/tasks/<任务>/` 内单独 `git init`。这是纯加法,session git 只看到软链,两个仓互不干扰。反而比复用 session git 干净:session git 若真盖到任务文件,checkout 回退会连带 spec.json、notes 等会话状态一起回退,粒度是错的。

### 2. 生图:确实是 codex,seed 一条作废,但 referenceImages 照样能用

（2026-08-01 订正。本节最初写成「产品内走 Gemini NB2 网关」,是错的,已按代码与 `.env` 实测重写。）

核实路径:`server/engine/mcp/tools/generate-image.js` 第 138 到 143 行、499 到 545 行。这个文件里有两条 provider 分支,由 `NODESIGN_IMAGE_PROVIDER` 分流,**默认值就是 `codex`**,注释写明「2026-07-27:NoDesk 网关退役,codex 成为默认 provider」。Gemini / DMXAPI 那条 gateway 分支只在显式设成 `gateway` 时才走,而且它要求 `NODESIGN_GATEWAY_KEY`,该变量在 `.env` 里不存在(实测 grep 只有 `NODESIGN_IMAGE_PROVIDER` 一个匹配)。所以线上生图**百分之百走 codex CLI**,骑订阅,零 API 费。文件头部那段描述网关协议的注释是退役前的遗留,已经和实际行为脱节。

对方案的影响:

- **seed 一条仍然作废**,codex 侧同样不暴露 seed。
- **`referenceImages` 照样可用**,两条分支共用解析(第 512 行),消费方式不同:codex 走 `-i` 附件传绝对路径,gateway 才转 base64 inline。限制是 codex 分支**不收 PDF 参考**,只收图片(第 539 到 545 行 fail-fast)。
- **flash / pro 两档路由是 gateway 专有**,codex 分支下 `model` 字段被写死成 `'codex'`(第 713、779 行)。所以「身份参考图用 pro 档生成一次」这句不成立,codex 下没有档位可选。
- **生图不进 API 账单**,只吃 codex 订阅额度和墙上时间(spawn `codex exec`,有超时和一次重试)。这对全景图的成本模型是好消息:插图数量不影响本文档第一部分算出的那些金额。代价在 1 核机器上是并发和时延,不是钱。

所以立绘一致性方案是:角色文件夹里存「冻结的 prompt 片段 + 一张身份参考图」,后续所有立绘与表情差分都带这张参考图走 `referenceImages`。身份参考图就用默认档生成,多试几次挑一张定死即可。

### 3. 「加形态只需注册表挂模块 + 前端加窗组件」:大体成立,但有三处例外

成立的部分:manifest 形状确实不用改。`artifacts` 是平列表,每条带 root / srcRoot,层级从路径前缀推出,`artifactOfPath` 已做前缀匹配(长的优先)。`ENTRY_FILE` 从注册表派生(`artifact-target.js` 42 行),新形态自动跟上。嵌套这件事基本全是加法,这点材料说对了。

例外的部分:
- `web/src/components/canvas/BoardCanvas.jsx` 的卡片派生有多处按 kind 硬编码分支(约 238、959、1211 行),world 的画布呈现必须动这里,不是只加一个窗组件。
- `api/exports.js` 有多处 `KIND_SITE` 特判(fit 注入、整站 zip 守卫),world 的导出格式接进去时要过一遍。
- `kinds/index.js` 的 `taskManifest` 是手写的 deck 与 site 两轮循环,不是遍历注册表,加 world 要在这里插第三轮。

### 4. 那组单价是 Sonnet 档,不是 Opus 档

输入 $3/M、输出 $15/M、缓存读 $0.30/M、1 小时缓存写 $6/M,这四个数内部自洽(1h 写 = 2 倍输入价,读 = 0.1 倍输入价),但它们是 Sonnet 4.6 / Sonnet 5 的牌价。Opus 5 牌价是输入 $5/M、输出 $25/M,对应缓存读 $0.50/M、1h 写 $10/M,约为材料数的 1.67 倍。实测的 opus 单轮 $2.5 到 $12 是 SDK costUSD 口径(订阅模式下是折算出来的额度值,不是实付)。

本文按约定用材料给的这组数估算。量级结论与倍数结论不受影响;需要 opus 牌价口径时,把绝对值乘 1.67。

### 5. 「缓存断点」不是手动摆的,分层图的机制描述要修正

Agent SDK 走自动前缀缓存,断点不由业务代码指定。分层缓存设计的结论全部成立(冻结世界书、变化追加在后、自然节点折叠),但落点是这样的:

- 「永不变层」= 系统提示。现状是 claude_code preset + NODESIGN_PRELUDE 静态追加(`session-loop.js` 450 行附近),SKILL 走插件惰性加载。world 的文风与纪律放 skill,不进常驻提示。
- 「几乎不变层」= 世界书文件。它不需要每轮注入:第一次被 Read 进对话历史后,后续轮命中前缀缓存,读价 0.1 倍。折叠改写文件本身不打缓存;打缓存的是重写后的世界书再次全文进入上下文的那一次。
- 「每轮变层」= UserPromptSubmit 的 additionalContext(`hooks.js` makeUserPromptSubmitHandler)。它追加在历史尾部,天然在缓存命中区之后,这正是断点之后的层。
- 「换模型 = 缓存作废」正确,缓存按模型隔离。

### 6. 小修正:任务与会话的物理关系

「任务 = 会话一对一」是逻辑约定(marker 认领),物理上 tasks 在项目共享目录,每个会话都看得见所有任务(`artifact-target.js` 头注释自己写明了这点)。这不影响设计,但所有「world 的状态」必须以任务目录为界,不能依赖会话目录里的任何东西。理由见漏洞第 4 条。

## 一、预期完成全景图

### 1. 一个 world 任务的目录结构

四槽位照旧:源(任务根)、产物根 dist/(导出物)、展品 _drafts/、忽略 .ndignore。world 的源比 deck 和 site 厚得多,因为世界状态本身就是源。

├── .git/                      per-task 历史(新 init,阶段 2)
├── .ndignore
├── 世界.md                     世界书。detect 证据 + 入口文件。冻结层,只在章末/场末折叠时改写
├── 事件.md                     断点之后的追加层:世界级变化先记这里,折叠时并进世界书
├── 大纲/                       小说模式

│   ├── 卷一.md                三层之二:卷

│   │   └── 皇宫/

「一个角色同时只在一处」由文件系统保证(一个文件夹只有一个父目录),这条性质在此结构下继续成立。角色移动 = 文件夹 mv。但角色需要一个不随路径变的 id(角色.md frontmatter),理由见漏洞第 2 条。

### 2. 形态契约怎么填

| 契约字段 | world 的取值 | 说明 |
|---|---|---|
| id / view | 'world' | 前端窗组件提示 |
| entryFile | '世界.md' | 判定证据之一;detect = 任务根有世界.md,或 marker.kind='world' |
| detect 次序 | KIND_ORDER 最前 | 必须排在 deck / site 之前,理由见漏洞第 8 条 |
| injectFit | false | 没有翻页语义 |
| exportFormats | ['handoff'],阶段 6 加 'book' | 仿书是导出格式不是窗 |
| referenceDoc | world-reference | 首次建世界时注入的技术参考,同 site-reference 机制 |
| artifactRoot | '' | 源即状态;dist/ 只装导出物 |
| discoverInstances | 递归扫 世界/,吐嵌套节点 | 每个地点 / 角色 / 容器一条,带相对路径,层级由前缀表达 |
| describe | 一行:当前场景、在场角色、场记或章进度 | 进每轮注入清单,是注入预算纪律的载体 |

### 3. 画布上打开一个世界看到什么

工作区里,world 任务不再是一张卡,而是一片嵌套区域:地点画成大的容器框(背景是该地点的背景.png 缩略图),地点里套子地点,角色画成小的立绘卡(512px webp 缩略图,走现有 image-variant 管线,原图不上墙)。角色库是一个视觉上与地点明确区分的容器(无背景插图,收纳态)。当前场景(会话正在演的那个地点)有明确的视觉标记。

拖一个角色从场景 A 到场景 B,等于提议一次 mv,走现有拖拽确认制:前端标记待定,用户确认后服务端执行 mv、git commit、通知 agent。拖到当前场景外等于下场,他的当前状态不再进 prompt,这一轮变便宜且他不再影响剧情。在场与否第一次成为一个可以直接用手操作的上下文预算开关。

### 4. 打开一个角色看到什么

点开角色是星形展开:中心是立绘(此时才加载原图),四周辐射各个面的卡片:当前状态、背景故事、经历(折叠显示,默认只见摘要头部)、立绘集。每张面卡可点开阅读或编辑,编辑落盘走 Canvas.write 通道并 git commit。关系不在星里:两个角色的立绘之间画边,点边打开关系文件。

### 5. RP 一轮的完整数据流

1. 用户输入(聊天,或先拖角色上下场再输入)。`api/turn.js` composeUserMessage 拼装:用户文本 + 托盘附件 + 素材提醒。
2. UserPromptSubmit hook(`hooks.js`)注入:路径地图、便利贴清单、产物清单。产物清单里 world 的 describe() 一行给出:当前场景路径、在场角色名单、场记进度、悬线文件存在提示。这一行就是每轮注入清单的执行点。
3. agent 按 world-craft skill 的纪律读文件:当前地点的 地点.md、在场角色各自的 角色.md、在场角色两两之间存在的关系文件、场记末尾若干条。第二轮起这些内容已在对话历史里,命中前缀缓存,只需读增量。背景故事与经历不读,需要时用工具按需查。
4. 生成回合。流式走现有 WS 快照加尾随范式推前端;v1 按纯文本尾随显示,回合完成后前端把落盘的场记解析成卡片(说话者是数据,见漏洞第 6 条)。
5. 落盘:场记文件追加本回合;剧情改变了谁的状态就 Edit 谁的 角色.md;世界级变化追加进 事件.md;世界书不动。
6. 回合末服务端动作:per-task git commit(一轮一条);经历条目计数(超阈值只做标记,压缩留给场末结算);manifest 刷新,前端按 fileVersions 局部刷新。
7. 计量照旧:absorbResult 差分,run_model_usage 落库。world 上线初期要按它盯每轮 input tokens,这是注入纪律是否守住的唯一硬指标。

RP 的回退:场末以内的「重说一句」走场记文件的句级重写(重 roll 最近一条,agent 改文件),跨场的「回退三轮」走 git checkout。两者语义不同,见漏洞第 1 条。

### 6. 小说一章的完整数据流

1. 开章:agent 读 全书.md、当前卷、上一章的 实际.md(不是计划),写 章-N-计划.md,commit。
2. 写作若干轮:读计划与正文尾部,写 正文/N-*.md 连续散文;人物状态按场更新;世界变化进 事件.md。
3. 章末结算(用户点「结束本章」,服务端注入一轮,一次做完四件事):对超阈值角色压经历(近期原文保留,往事压成摘要,同 WS 快照加尾随的形状,git 保底所以敢有损);把 事件.md 折叠进 世界.md;写 章-N-实际.md;写下一章骨架。commit。
4. 结算后建议结束会话。下一章新会话冷启动,只靠文件重建上下文。这是防成本递增和防 compact 丢失细节的主要手段,见漏洞第 4 条。

### 7. 成本量级估算

单价按材料给的那组(勘误第 4 条:这是 Sonnet 档牌价;换 Opus 5 牌价乘 1.67):输入 $3/M,输出 $15/M,缓存读 $0.30/M,1h 缓存写 $6/M。

RP 一轮,架构做对(注入清单守住,历史靠前缀缓存,不换模型):
- 历史缓存读约 100k 到 200k tokens,$0.03 到 $0.06;本轮新增写缓存约 3k 到 5k,$0.02 到 $0.03;输出 1k 到 2k,$0.02 到 $0.03。agent 内部一轮约 3 到 5 次 API 往返,每次重付一遍缓存读。
- 合计每轮 $0.10 到 $0.25。与 sonnet 实测每轮 $0.11 吻合。一晚 50 轮约 $5 到 $12,单日 $15 限额玩得起。

RP 一轮,架构做错(世界书加全角色经历每轮全量重进,或频繁换模型作废缓存):
- 80k 到 100k tokens 按缓存写价 $6/M 算就是每次往返 $0.5 到 $0.6,乘 3 到 5 次往返,再叠加历史全价重读的递增。
- 每轮 $2 到 $12,与 opus 实测两小时从 $2.5 递增到 $12 的曲线同形。50 轮要 $150 以上,单日限额只够 5 到 10 轮。两个口径差 20 到 50 倍。

小说一章,架构做对:
- 输出约 8k 到 15k tokens($0.12 到 $0.23);10 到 20 轮工具往返的缓存读合计约 $0.5 到 $1;增量缓存写约 $0.2;章末结算折叠 5 万 token 世界书,重建约 $0.30 写价加处理轮,约 $0.5 到 $1。
- 合计每章 $1.5 到 $3。四十章约 $60 到 $120,分摊到几十天,可行。

小说一章,架构做错(无折叠纪律、不换会话、世界书每轮重进):
- 每轮 100k 级全价或写价输入,30 轮每章 $20 到 $30,且随书变长线性变贵。第四十章一章就能打穿单日限额。

结论:做对与做错之间差一个数量级以上,而分界线就是三条纪律:注入清单、折叠节点、会话按章丢弃。这三条都必须由服务端或结构保证,不能靠 agent 自觉。

## 二、分阶段 plan

划分原则:每个阶段结束都是一个可停手的完整状态,不留半成品;能跑什么、看什么算完,逐条写死。

### 阶段 0:注册表挂上 world(半天)

做什么:新建 `server/lib/kinds/world.js`(id / entryFile='世界.md' / detect / artifactRoot / manifest / describe 最小实现,discoverInstances 先只吐世界根一条);`kinds/index.js` 挂进 KINDS,KIND_ORDER 把 world 放最前;taskManifest 插第三轮循环。

动了现有代码:仅 `kinds/index.js`。影响面是全部任务的形态判定次序。回归风险:world 的 detect 证据(世界.md)如果宽了会误吞 deck / site 任务。控制手段:detect 只认「任务根存在 世界.md 或 marker.kind='world'」;跑 `_kinds-check.mjs`;再写一个一次性脚本对线上全部任务跑 taskManifest,diff 加 world 前后的输出必须完全一致。

完成判据:手工建一个含 世界.md 的任务目录,API `/tasks` 返回 kind='world';现有任务的 manifest diff 为零。

### 阶段 1:嵌套节点发现与画布渲染(第一刀的主体)

做什么:world.js 的 discoverInstances 递归扫 `世界/`,按内容证据(地点.md / 角色.md / 容器.md)吐嵌套节点,每条带相对路径与类型;`api/assets.js` 的 tasks 清单透传;BoardCanvas 加 world 分支:地点大框、角色立绘小卡(有图用 512 缩略图,无图占位)、容器收纳态。本阶段只读不写:不做拖拽 mv,不做星形展开。

## 三、漏洞与自相矛盾

按严重程度排序。

### 1. git 前提不成立,且两种「回退」语义互相打架

前提问题见勘误第 1 条,修法明确(per-task git)。更深的问题是:材料把「重 roll 某一句」和「回退三轮」都归给撤销,但它们是两套机制。git checkout 的粒度是整棵任务树,回退三轮会把这三轮里发生的角色状态变更、经历追加、角色移动全部一起回退,这通常正是用户想要的;而「只重 roll 某一句、保留之后的剧情」在 git 语义下根本不存在,它是对场记文件的一次句级编辑,编辑之后「之后的剧情」与被改的那句可能矛盾,谁来对齐没有答案。建议 v1 定死:重 roll 只允许最近一句(此时没有「之后」需要对齐);更早的句子想改,等价于 checkout 到那一句再走新分支。把这条写进 world-craft 和 UI,别让两种撤销出现在同一个菜单里装作同一件事。

### 2. 「路径即身份」与「移动即操作」相乘,身份是不稳定的

设计说「谁在哪不需要第二份数据结构,它就是路径本身」。但路径同时也是所有引用的键:board.json 的布局坐标、上下文托盘的引用、fileVersions 的版本表、activeArtifact 的会话记录、评论锚点,全部按路径寻址。角色一 mv,这些引用全部悬空:立绘卡的坐标丢了,托盘里的引用指向不存在的路径。项目已有的教训(画布锚点必须盖稳定 id,评论错位查了三轮)就是同一个问题。修法:角色.md frontmatter 里放一个不变的 id,画布与引用层一律按 id 寻址,路径只表达位置。要诚实承认:这意味着「不需要第二份数据结构」只在「谁在哪」这一个问题上成立,引用层事实上永远是第二份数据结构,mv 时服务端要按 id 做一次引用迁移。

### 3. RP 与小说共用角色状态,时间线会打架

同一个世界先写小说再开 RP(这是最自然的玩法:写完书进去玩),角色.md 只有一份,但小说线的「当前状态」在第四十章,RP 想从第三章的状态开玩。branch 能隔离文件,但整个上层没有 branch 概念:画布只渲染 checked-out 的那棵树,manifest、封面、评论都不知道分支存在,双线并行时另一条线在产品里不可见。建议 v1 明确降级:一个 world 任务同一时刻只有一条活线;git branch 只用于「这条线不要了」的归档,不提供并行宇宙;想从第三章状态开 RP,就 checkout 出来另存一个新任务。并行宇宙是个真需求,但它是 v2 的产品问题,不是 v1 的 git 问题。

### 4. 「任务 = 会话一对一」与「一个世界长跑几百轮」根本冲突,材料没写破

一条会话跑四十章必然撞 900k 自动压缩,压缩产生的摘要恰恰会丢失 RP 最依赖的口吻和细节;不压缩则成本按实测曲线递增(两小时三倍的根因就是历史累积)。设计里「文件即真相」其实已经隐含了答案,但必须把它写成硬规则:会话是消耗品,世界只活在文件里。任何一轮结束后删掉会话,新会话只靠读文件必须能无损续上;章末 / 场末结算就是天然的换会话点,结算的产出(折叠后的世界书、压缩后的经历、实际大纲)必须足够让冷启动不掉质量。这条应该作为验收标准写进阶段 3 的判据(模拟中途强制换会话,续写质量不塌),而不是一个优化建议。顺带,这也是对「延迟不是约束」的补强:换会话的冷启动首轮贵一点慢一点,在这个用户群完全可接受。

### 5. 每轮注入清单管得住 hook,管不住 agent 自己的 Read

未拍板 B 把预算定在注入清单上,但真正的膨胀源有两个:历史累积(第 4 条已答)和 agent 的好奇心。它一次 Read 某个老角色的经历全文,预算就翻掉了,而工具层没有按文件粒度的读禁令可用。能做的:describe() 里明示「经历与背景故事勿全文读,用检索」;经历文件本身分卷(经历-近期.md 加 经历-卷N.md),把「全文读也不大」变成结构性质;world-craft 写明纪律;最后靠 run_model_usage 的每轮 input 监控当回归测试。要承认这是软约束加监控,不是定死。定死的假象比软约束更危险。

### 6. 卡片编排、散文、仿书是三套渲染,流式分块被低估了

「一个说话者一块地流」要求结构化流式输出:要么 agent 按约定分隔符写(格式一漂前端就裂,而 agent 在长会话里一定会漂),要么服务端增量解析半成品文本。现有 WS 快照加尾随是纯文本范式,块级流式是一套新协议。建议 v1 砍掉「流式中就有卡片」:落盘格式统一为带说话者标注的 markdown,流式期间纯文本尾随(用户看得到字在出),回合完成后由前端解析落盘文件转成卡片。说话者立绘随发言实时反应这类演出,推迟到协议稳定之后。这样三套渲染变成:一套落盘格式,两个读取器(卡片视图、散文视图),仿书是第三个读取器但离线运行(导出时),维护成本可控。

### 7. 1 核 3.9G 机器上的两笔账:前端流量与后端内存

前端:生图原图动辄数 MB,二十个角色加每层背景插图,直出原图首屏就是上百 MB,Spot 机的带宽和用户的浏览器都受不了。image-variant 缩略图管线(512px webp 约 50KB)已经存在,world 必须从第一天就全量走它,原图只在星形展开的中心态按需加载。这要写进阶段 1 的实现而不是后补。后端:rembg 的 birefnet 系模型单次推理峰值 2.4GB 以上(remove-background.js 注释实测),机器总共 3.9G 且已用一半,与 node 并跑一次就可能 OOM 把线上打死。立绘批量抠图必须串行、压质量档(NODESIGN_REMBG_QUALITY_CAP 已有),并且不要在有用户会话跑图的同时批量抠。

### 8. detect 抢跑:world 任务里出现 html 会被 deck / site 抢走

deck.discoverInstances 把任务根顶层每个 .html 都算一份 deck;site.detect 认任务根或约定目录里的 index.html。world 任务一旦导出仿书或 agent 随手写个预览页,现有次序下这个任务会被判成 deck 或 site,或者 manifest 里凭空多出 deck 卡。对策:KIND_ORDER 里 world 最前且 detect 证据强(世界.md);world-reference 写明导出物只进 dist/;dist 在 site 的 OUTPUT_DIRS 探测名单里,所以还要在 world 命中时短路后续判定(detectTaskKind 本来就是首个命中即返回,顺序对了就安全,但 taskManifest 的多产物循环是并列跑的,需要在 world 命中时抑制 deck / site 的实例发现)。这条是阶段 0 回归脚本要重点盯的。

### 9. 关系只说了「是边」,没说存哪、怎么进 prompt

关系是对象渲染成边,拍板了。但材料的嵌套规则里没有它的位置:放在某个角色文件夹里就退回「两张卡各自漂移」的老问题。建议:任务根 `关系/` 平放,一对角色一个文件,文件名用两个角色名按字典序连接,保证一对只有一份。注入规则:每轮只注入「在场角色两两之间存在的关系文件」,不在场的人的关系不进。这同时回答了检索问题:按在场名单过滤文件名即可,不需要索引。

### 10. 立绘 prompt「冻死不许 agent 改」缺执行机制

agent 的 Edit 工具对任务目录是全开的,SKILL 里写「不许改」是软约束,和「系统提示要求 agent 注意到数量超了不可靠」是同一类错误,材料一边识破了后者一边在前者上重犯。可行的硬化:PostToolUse hook 对 `立绘/prompt.md` 的写操作直接拦截并注入警告(hooks 基础设施现成);或者干脆把 prompt 片段放进 `.nd-task.json` 这类 agent 约定不碰、且有 marker 兜底地位的文件。二选一,但要有一个是硬的。

### 11. 角色文件的并发写没有锁

回合内 agent 写 角色.md,同时用户可能在星形展开里编辑同一个文件(Canvas.write 通道)。spec.json 曾经因为三处无锁读写丢过数据,后来上了 per-path mutex。角色文件走同样的路:写通道统一过 mutex,或至少 agent 回合期间锁编辑入口(现有「会话跑动时禁部分操作」的机制可复用)。

### 12. 两个未拍板决定的立场

A(文件夹属性判定):支持内容证据,反对命名约定。三条理由材料已有,补一条:嵌套发现是递归扫描,类型判定要在每一层做,命名约定意味着显示名永远背着类型前缀或者要一张前缀解析表,而内容证据让「重命名永远不弄坏东西」在整棵树上成立。kinds/index.js 头注释「文件会被改,marker 不会,让不会变的当兜底」是项目自己的判例,照抄即可:内容文件当权威,marker 当兜底。此立场仅供拍板参考。

B(每轮注入清单):支持材料建议的清单(当前地点 + 背景 + 在场状态 + 本章大纲 + 近期对话,背景故事与经历按需工具读),预算 15k 合理。但要加两条配套才成立:经历分卷让「按需读」不至于一读就爆(第 5 条),以及 run_model_usage 的每轮监控当作这条清单的回归测试。清单本身写进 world-craft 与 describe(),在写第一行引擎代码之前定稿。
